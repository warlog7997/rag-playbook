# Chapter 3 — Irrelevant Results (Right File, Wrong Section)

## The Real Story

After fixing retrieval with hybrid search, we noticed a new problem. Results were technically
from the right file, but the top-ranked chunk was always the **introduction or overview section**
— not the specific answer.

The introduction sections of our healthcare platform docs mentioned every topic covered in
the file. "Authentication," "SSO," "two-factor," "session management" — all appeared in the
first paragraph. So for almost any query about authentication, the intro scored highest.
The actual detailed instructions were buried at rank 3, 4, or 5.

Users were getting answers like: "NovaDash supports two-factor authentication via TOTP and
SMS fallback, and you can configure this in the security settings." Accurate but useless —
no steps, no instructions, just the intro paragraph repeated.

Reranking was the fix.

---

## The NovaDash Equivalent

**Query:** "How do I set up 2FA?"

The `authentication.md` file has:
- An **intro section** that mentions: "...two-factor authentication (TOTP, SMS fallback)..."
- A **Two-Factor Authentication section** with step-by-step setup instructions

Without reranking, the intro ranks #1 because it broadly matches many authentication queries.
The specific 2FA section with actual instructions ranks #3.

After reranking, the 2FA section moves to #1 because a reranker is specifically asking:
*"Does this chunk answer the user's question?"* — not just *"Does this chunk contain related words?"*

---

## Retrieval vs. Reranking

Think of it as a two-stage funnel:

```
All 80+ chunks
      │
      ▼ Stage 1: Retrieval (fast, approximate)
      │  Hybrid search → top 15 candidates
      │  Goal: don't miss the right answer (high recall)
      │
      ▼ Stage 2: Reranking (slower, precise)
         Reranker scores each (query, chunk) pair directly
         Goal: move the best answer to #1 (high precision)
```

Retrieval is optimized for recall (cast a wide net). Reranking is optimized for precision
(rank the net's contents correctly). This division of labor is why the two-stage approach
works so well.

---

## Approach 1: Cross-Encoder Reranker

A **cross-encoder** takes a (query, document) pair as a single input and outputs a relevance
score. Unlike bi-encoders (which embed query and doc separately), cross-encoders let the two
texts "see" each other — enabling fine-grained comparison.

Model: `cross-encoder/ms-marco-MiniLM-L-12-v2`
- Trained on the MS MARCO dataset (web search relevance judgments)
- Fast: runs locally, no API call needed
- Limitation: trained on web search queries, may not understand SaaS domain terminology

**Speed:** ~50ms per (query, chunk) pair on CPU. For 15 chunks, that's ~750ms total.
Acceptable for interactive RAG, but adds latency.

---

## Approach 2: LLM-as-Reranker

Instead of a fine-tuned cross-encoder, use Claude Haiku to score each chunk.

```
For each chunk, ask:
"On a scale of 1-10, how relevant is this documentation chunk to the query?
Return JSON: {"score": 7, "reason": "Contains setup steps for..."}"
```

**Pros:**
- Understands SaaS domain terminology (Claude has seen product docs in training)
- Can handle semantic gaps better than a web-search-tuned cross-encoder
- Can be prompted to weight different aspects (e.g., "prefer step-by-step instructions")

**Cons:**
- Slower: 1 API call per chunk → 15 chunks = 15 API calls (~3-5 seconds)
- More expensive: 15 Haiku calls per query
- Non-deterministic: scores can vary slightly between calls

In practice, LLM reranking is excellent for high-value queries where accuracy matters more
than speed. For real-time chat, cross-encoder is usually the right trade-off.

---

## Approach 3: Contextual Embeddings

Instead of fixing the ranking *after* retrieval, fix the embedding *before* indexing.

The problem: a chunk like "## Two-Factor Authentication\nSetup:\n1. Go to Profile..." has
a poor embedding because it's instruction-heavy and keyword-sparse. The intro section
embeds better for queries like "how does 2FA work" because it has a richer overview.

The fix: **prepend a context sentence** generated by an LLM that explicitly describes
what the chunk is about and what question it answers.

```
Original chunk:
  "## Two-Factor Authentication\nNovaDash supports two 2FA methods..."

Enriched chunk:
  "This section explains how to enable two-factor authentication in NovaDash,
  covering TOTP setup with authenticator apps and SMS fallback configuration.
  ## Two-Factor Authentication\nNovaDash supports two 2FA methods..."
```

The enriched chunk embeds much better for queries like "set up 2FA" or "enable MFA."

**Cost:** One Claude Haiku call per chunk at ingest time. For 80 chunks, that's ~$0.05.
Done once at ingestion — no extra cost at query time.

## Key Takeaway

> Retrieval gets the right *file*. Reranking gets the right *section* within the file.
> Don't skip reranking when answer quality matters.
